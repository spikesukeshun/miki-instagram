# rules/threads.md — Threads 1か月実験（2026-10〜）

Instagram の過去投稿を Threads 向けに書き直して1日1投稿し、1か月で
**認知・エンゲージメント・プロフィールへの関心・問い合わせ/予約** につながるかを確かめる実験。
Threads API をつなぐこと自体は目的ではない。

- 文体・ブランド・禁止事項の正は `SKILL.md`（Threads でもそのまま守る）。ここには Threads 固有のことだけを書く
- 機械で止められるルールは `threads_plan.py review` と `threads_scheduler.py` の投稿前チェックに実装している。
  数値の上限はコードの定数が正（`threads_api.TEXT_LIMIT` など）

---

## 1. 投稿文の生成ルール（Claude Code が週次で書く時に毎回読む）

### 入力と出どころ
- 入力は `threads/pool.json` の1件（元IG投稿のキャプション全文・テーマ・メディア種別）
- **書いてよい事実は「元キャプション」と「`SKILL.md` の現行情報」だけ。** 足りない事実は書かない
- 価格は `SKILL.md` に載っている金額だけ（review が照合する）。元キャプションの古い価格（`outdated_prices`）は使わない
- 空き状況は **手入力された空き情報がある日だけ**（`availability` 欄）。無い日は「空いています」「今日行けます」系を一切書かない
- 地域名は **六本木のみ**（MIKIの勤務地）。他の地名は書かない
- 「Instagram限定20%OFF」（古い投稿の「初回限定20%OFF」も）は Instagram の特典なので Threads では出さない。サロン名（AMRTA）も書かない
- 効果の断定（治る・完治・確実に・100%）は禁止。「絶対」「必ず」は原則使わない

### 型（毎回1つ選ぶ。分析の単位）
元投稿の内容に合う切り口を選ぶ。同じ型を2日続けない。

| 型 | 合う元投稿 | 書き方の芯 |
|---|---|---|
| 悩み起点 | 肩こり・むくみ・肌荒れなどの話 | 「こういう状態、ありませんか」から入り、MIKIの見立てを1つ |
| 施術紹介 | メニュー・施術の流れ・ビフォーアフター | 何をする施術かを一言で。感想や変化は元投稿にある範囲で |
| 人柄・こだわり | MIKIの経験・資格・考え方・弱み | 一人称「私」で、なぜそうしているか |
| 利用シーン・季節 | ご褒美・ブライダル・季節の話 | 「こういう日に来る方が多い」「この季節は〜」 |
| 価格・キャンペーン | 価格に触れた投稿 | 現行価格のみ。煽らない。月に数回まで |
| 会話・問いかけ | 誰でも答えられる話題 | 具体的な二択・一問で終える（例: 肩とむくみ、どっちが気になる？） |
| 当日の空き | 空き情報が手入力された日だけ | 冒頭に日時と枠。次に「こんな人に」。予約導線はDM |

参考例（地域→施術→空き→特別価格→悩み→特徴→予約 を全部入れる構成）は
**「当日の空き」型の1パターン**として扱い、毎回のテンプレートにはしない。
7要素を毎回詰めると500字の広告文になり、会話が生まれにくく宣伝色が強くなるため。

### 書き方
- 150〜350字が目安（上限はコードで判定）。Instagram 本文の要約ではなく、**1つの話題だけ**を切り出す
- 冒頭1〜2行で「誰の・どんな状況の話か」が分かるようにする。冒頭の書き出しは週内で重ねない
- 改行多め。絵文字は0〜3個
- 地域名（六本木）と施術名は、文として自然な時だけ入れる。キーワードを並べない
- 本文にハッシュタグは書かない。**トピックは `topic_tag` で1つだけ**付ける
- CTA（DM・予約・ご相談）は**内容上必要な時だけ**。1週間で半分以下
- 問いかけは具体的なものだけ。「いいねして」「フォローして」等の反応を求める文言は禁止（エンゲージメントベイト扱い）

### topic_tag（毎回1つ、1〜50字、「.」「&」「#」なし）
投稿内容に本当に関係するものを1つ選ぶ。種類ごとに閲覧数を比べるので、3系統を偏りなく使う。
- 地域系: 六本木エステ／六本木
- 施術ジャンル系: フェイシャル／ブライダルエステ／ヘッドスパ など、その投稿の施術名
- 広域系: 美容／リラクゼーション／エステ

### 属性（review が本文から自動判定して記録する）
地域・問いかけ・CTA・空き・価格 は自動判定。**悩み** だけは Claude が `flags` に書く（悩みから入る投稿のとき）。

### メディア
- `threads/pool.json` の `media_suggest` を初期値にする
- カルーセルは先頭から最大4枚（末尾2枚は Instagram 用の CTA スライドなので使わない）
- リールは表紙画像（`thumbnail`）。Instagram の音源ライブラリを使った動画を Threads に再アップロードする権利が不明なため。自分で撮った音源の動画だけ `video` にしてよい
- 画像の取得に失敗した日はテキストのみで投稿され、シートの「投稿メディア_実際」に残る

## 2. 週次の作業手順

```bash
# 0. 未使用の候補プールを作る（読み取りのみ）
/usr/bin/python3 threads_plan.py export --insights

# 1. その週の各日の時間枠を見る（--experiment-start は実験初日）
/usr/bin/python3 threads_plan.py slots --start 2026-10-13 --days 7 --experiment-start 2026-10-06
```

2. この文書と `SKILL.md` を読んでから `threads/week_YYYY-MM-DD.json` を書く（形式は `tests/fixtures/threads_week_sample.json`）
3. 機械チェック（省略不可）。❌ が出たら直して再実行：

```bash
/usr/bin/python3 threads_plan.py review threads/week_YYYY-MM-DD.json
```

4. シートの `threads_posts` タブへ登録（ステータス「確認待ち」。review に ❌ があると登録しない）：

```bash
/usr/bin/python3 threads_plan.py register threads/week_YYYY-MM-DD.json
```

5. シートで「本文」を確認・修正し、ステータスを「承認済み」にする。「本文_生成時」は触らない（修正率の計算に使う）
6. 作業にかかった分数を `threads_daily` タブの「作業時間_分」に書く

### 空きが出た日
シートのその日の行の「空き情報」に事実（例: `10/8 15:00 1枠`）を書き、Claude Code に
「今日の Threads を空き告知に差し替えて」と頼む → 本文と型を書き換えて review の基準で確認する。
空きに触れる本文は、空き情報欄が空だと投稿前チェックで止まる（「要確認：」になる）。

### 問い合わせ・予約
「Threadsを見て」と言われた問い合わせ・予約は、きっかけになった投稿の行の「問い合わせ件数」に足す。
どの投稿か分からない場合は、その日の行に入れて「メモ」に書く。**ここが空だと予約への効果は判断できない。**

## 3. 自動で動くもの（`.github/workflows/threads.yml`）

| 時刻（JST） | 処理 |
|---|---|
| 8:00 / 12:30 / 21:00 | `threads_scheduler.py post` — 予定時刻を過ぎた「承認済み」を1件だけ投稿 |
| 5:00 | `threads_scheduler.py insights` — 投稿別（24時間・7日時点・最新）とアカウント日次を記録 |

- JSTの同じ日にすでに投稿済みなら投稿しない（1日1投稿）。予定から6時間以上遅れた行は出さない
- 公開に成功したら、最初にステータスを「投稿済み」にする。その後の失敗では「エラー：」を書かない（再投稿防止）
- API失敗は「エラー：」＋LINE通知（同じ日の次の枠で再試行）。投稿前チェックで止めたものは「要確認：」（人が直すまで出ない）
- `THREADS_ACCESS_TOKEN` が未設定の間は何もせず成功終了する
- Instagram の `post.yml` / `post_scheduler.py` / シート1枚目には一切触れない

## 4. 実験の設計

- 期間30日・1日1投稿。最後の投稿の7日後にレポートを作る：
  `/usr/bin/python3 threads_report.py --start <初日> --end <30日目>`
- 同じ Instagram 投稿は実験中に1回だけ（register と投稿前チェックの両方で止める）
- 投稿時間テスト: 朝・昼・夜の3枠を日ごとに回し、週ごとに1つずらす（`threads_plan.slot_for`）。
  IG は月22/木21/金22時に固定しているため時間帯データが無く、第三者データ（平日朝が強い・日本のデータなし）と
  IGの実績（夜）の両方を試す。型や曜日が枠ごとに完全にはそろわないので、差が小さければ時間の効果と断定しない
- ロケーションタグ・コミュニティは1か月目は使わない（変数を増やさない。コミュニティは API 非対応）
- 返信への対応は MIKI さんが手動で行う（公式に「返信は閲覧の約半分を占める」とされる）

### 評価（4つの層に分ける。数値だけで Instagram と優劣を決めない）
| 層 | Threads で見るもの |
|---|---|
| 認知 | 投稿の views（公式に「開発中」表記。取れない場合はレポートに明記） |
| エンゲージメント | likes / replies / reposts / quotes / shares |
| プロフィールへの関心 | アカウント views（＝プロフィール閲覧数）、followers_count の日次推移、clicks（プロフィールのリンク） |
| 問い合わせ・予約 | シートの手入力 |

## 5. Threads API の設定（最初に1回・手動）

1. developers.facebook.com でアプリを作成し、ユースケース「Threads API にアクセス」を追加
2. 権限: `threads_basic` / `threads_content_publish` / `threads_manage_insights`
3. アプリの「ロール」で MIKI さんの Threads アカウントを **Threads Tester** に追加し、
   Threads 側（設定 → アカウント → ウェブサイトのアクセス許可 → 招待。画面名は変わることがある）で承認する。
   自分のアカウントだけに投稿するので App Review は不要
4. 認可 → 短期トークン（1時間）→ 長期トークン（60日）に交換。ユーザーIDを控える
5. `~/.zshrc` と GitHub secrets に登録: `THREADS_ACCESS_TOKEN` / `THREADS_USER_ID`
6. 接続確認（書き込みなし）: `/usr/bin/python3 threads_api.py --check`
7. 期限前の更新: `/usr/bin/python3 threads_api.py --refresh` → `~/.config/miki-threads/new_token.txt` に保存された新トークンで 5 を置き換え、ファイルを削除する（トークンは画面・ログに出さない）
   （1か月の実験は1回の発行で足りるが、延長する場合は50日目ごろに更新する）

Instagram の `INSTAGRAM_ACCESS_TOKEN` は Threads には使えない（別のアプリ・別のトークン）。

## 6. API でできないこと（手動で扱う）
- 予約投稿機能 → GitHub Actions で代替
- コミュニティへの投稿、投稿の編集
- フォロワー増加の履歴 → 毎日 followers_count を記録して差を取る
- 投稿ごとのリンククリック（clicks はアカウント単位）
- DM・予約がどの投稿から来たか → 手入力

## 7. 実装の理由（変更するときに読む）
- **別タブに記録**: シート1枚目は A〜H 固定（CLAUDE.md）。Threads は列が多く手入力欄もあるため別タブにした
- **別ワークフロー・別スクリプト**: Instagram の自動投稿に影響を出さないため。既存ファイルは変更していない
- **生成は Claude Code の週次作業**: Anthropic API の従量課金を増やさず、投稿前に人が確認できるようにするため
- **メディアは投稿直前に Instagram から取り直す**: 投稿画像は投稿後に GitHub から削除される運用で、
  Instagram の media_url は署名つきで期限があるため
- **事実ルールをコードで止める**: 文章だけのルールは守られなかった経緯がある（rules/incidents.md）
